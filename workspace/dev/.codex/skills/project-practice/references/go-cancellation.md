# Go 请求取消与资源清理：出题前核对

用于讲解、编程作业和进阶迁移，不是固定模板或完整答案。

## 生命周期

Go 服务端请求的 Context 会在客户端连接关闭、HTTP/2 请求取消或 ServeHTTP 返回时取消。因此“handler 立刻返回，再把 r.Context 交给长期后台任务”不是让任务一直等到客户端取消的正确模型。[官方 Request.Context 文档](https://pkg.go.dev/net/http#Request.Context)

请求范围内的工作：handler 等待工作正常完成或请求取消，再返回。任务确实要超出请求存活时，必须使用应用级任务管理及明确的取消/超时策略；这是另一个设计，不靠请求 Context 偷偷延长生命周期。

仅在 time.Sleep 前检查一次 ctx.Done 不能中断已经开始的 Sleep，最坏仍等待这段 Sleep 完成；若要求快速取消，耗时等待本身要同时 select 定时器与 ctx.Done。不要给出 select/default + Sleep 却承诺“立刻退出”。

## 必测三条路径

1. 正常完成：不主动取消，任务实际完成，并返回预期结果；不能用任务一开始就退出冒充成功。
2. 主动取消：先通过 started 通道等确认任务开始，再触发取消，限时等待该任务自己的 done 通道/WaitGroup；避免用随机 sleep 当同步。
3. 清理：正常与取消路径都释放资源；所有 worker 退出，信号量归还，响应体 Close，后续任务仍可运行。

共享计数使用 atomic 或 mutex，不能在 goroutine 中无保护地修改全局 running 却要求 `go test -race` 全绿。展示有竞态的反例时必须标明“错误版本”，修复页不能沿用它。

`runtime.NumGoroutine()` 是整个进程的数量，包含 HTTP 与运行时任务；只作辅助趋势观察，不能要求它精准等于初始值作为唯一泄漏验收。以自己创建的任务退出和资源归还为主要断言，再补 `go test -race -count=3 ./...`。

## 教案审查

逐一检查正文、修复代码、选择题答案、作业标准是否描述同一生命周期。把“暂时继续工作”和“永久资源泄漏”区分开；有限时长任务自然结束不证明已支持主动取消，也不一定是永久泄漏。

反例必须可重复，不能依靠 goroutine 的调度顺序：handler 立即返回会取消请求 Context；若 worker 之后才先进入 ctx.Err 检查，它可能直接退出，并不进入 Sleep。不能把这种反例描述为“必定五秒后打印”，也不能在 HTTP 响应已正常结束后用 curl 超时声称复现了请求中途取消。教学对照优先让错误版和修复版都等待任务结束，只保留 Sleep 不可中断这一差异；通过 started 明确任务已进入待测耗时阶段，再取消。若展示多个错误并存的原始实现，应明确列出不同调度下的结果，不设置唯一错误预测答案。

红绿测试始终断言预期正确行为，例如“取消后本任务限时退出、资源归还”。错误实现下该断言失败，修复后同一个断言成功。若另写“资源仍未退出”来确认反例，那是反例观察测试，不能把它称为修复前红、修复后绿的同一测试；禁止要求学生修好后反转断言来制造全绿。
