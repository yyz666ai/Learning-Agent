# Plan 与课件：生成性能和可靠性排查

日期：2026-08-30。范围：本项目 Codex CLI → DeepSeek → Plan / 首章 HTML PPT 数据的生成链路。

## 先回答：为什么生成 Plan 会反复调用工具？

普通 Plan 不需要重新认识用户。前面确认的画像、目标、基础、节奏、约束和诊断结果应直接作为输入。之前把“读 Skills、找画像、读知识地图、研究资料、规划、写文件”都交给通用代理自行执行，容易产生重复读取和不必要的工具回合。

现在普通稳定课程的流程是：

1. Python 一次准备当前用户画像、对应 Skills 和准确匹配的主题知识地图。
2. Codex CLI 调用项目配置的 DeepSeek 生成完整 Markdown Plan，禁用工具和思考；不重新 onboarding。
3. Python 规范化等价 Markdown 结构并检查完整性。合格后事务保存为待确认草案。
4. 用户明确确认，才生成首章课件 JSON；前端用现有 HTML PPT 组件渲染。
5. 格式不合格时允许一次有界修正；最终仍不合格则保留旧内容，不假称成功，不无限重试。

知识地图是可选课程素材，不是机械全选的固定目录。未知主题、新框架、明确版本敏感需求、岗位资料研究仍保留必要检索。已验证且可复用的研究资料不应反复查询。普通 Go / Python 稳定基础大纲不因“完整掌握路线”就强制联网。

## 找到的实际问题

### 1. 请求参数关闭思考，但实际仍产生大量思考 token

在本机实测中，直接请求能遵循 `reasoning.effort=none`，而带 Codex User-Agent 或 `X-Codex-Turn-Metadata` 的请求会进入不同的兼容行为，即使同样传 `none` 仍产生思考 token。这是本次接口实验观察，不是对供应商所有版本的永久结论。

仅减少工具调用后，一个 Plan 仍用约 259 秒、约 2.5 万思考 token。因此“已经在配置里关闭思考”不能作为验收证据，必须看实际返回的 usage。

修复保持 Codex CLI：针对官方 DeepSeek 的本项目生成请求，启动一次性本机 Responses 转发器，仅转发固定官方端点。它去掉上述兼容元数据，显式传递 `none`；普通生成不提供工具，课件使用 JSON 输出模式。转发器仅监听本机，使用随机临时令牌，不把真实 API key 交给本地请求方，不打印密钥、不改变个人配置。研究脚本仍使用项目真实 API key，不会把临时本机令牌发往公网。

### 2. 模板与解析器对不上，误把学习目标当知识点

模板给出“必要知识点”，原解析器主要识别 `#### 知识点`。模型照模板输出时，解析器可能忽略真正知识点，退回到“本阶段要学”的长句。随后课件覆盖检查用这句长句作为匹配目标，制造后续误失败。

现在模板使用统一结构；解析器也接受“必要知识点”的明确行内枚举与缩进列表，并保留括号、代码中的分隔符。缺少展示用一级标题的完整结构化 Plan 可以补主题标题；不会凭空补学习内容，也不会把不完整草稿放行。

### 3. 过程说明污染最终产物

原驱动拼接所有 agent_message，可能把过程说明、带括号的推演和最终 JSON 混在一起。生成任务现只取最后完整回复，并要求成功终态和正常退出。失败前输出的部分 Plan 不能保存成成功结果。普通交互聊天的行为不变。

### 4. 教学规则与前端结构不一致

面试题曾被另建为总结页之后的 practice 页，违反最后一页必须是 mastery 的渲染契约。现明确由顶层 `interview_prompts` 统一进入最后一页和题库。

代码注释、渐进代码页、知识点覆盖的错误也提供具体页面和修正要求。不会为了通过测试，删除练习要求或跳过课程校验。

## 实测记录

所有真实调用均使用隔离测试用户。完整重跑和旧 Plan 回放分别记录；回放的 0 秒不计为真实生成速度。

| 样本 | 观察 |
| --- | --- |
| 修复前普通 Plan | 约 259 秒，23 次工具调用；约 1.5 万思考 token |
| 只预加载资料、尚未修复请求兼容 | 约 259 秒，0 次工具调用；仍约 2.5 万思考 token |
| 修复请求兼容后的 Plan 样本 | 已测到约 19–69 秒；非思考。但部分样本暴露模板问题，因此不能全部记为成功 |
| Go 精进课件，沿用已确认的真实生成 Plan | 首次 22.31 秒 + 一次修正 15.20 秒，通过保存校验；0 工具调用、0 思考 token |

以上是小样本，不是平均延迟、P95 或服务承诺。长大纲和密集章节仍需输出数千 token，不能承诺秒出。

最新零基础测试，两次调用都为 `tool_calls=0`、`stream_errors=0`、`reasoning_output_tokens=0`。对应记录目录 `evals/runs/20260830-223622-lesson-retest/`。其他记录目录为相应时间的 `*-lesson-retest/`；测试数据不进入 GitHub。

**结论：常规生成的性能问题和多处结构误判已修复，但尚未达到“所有路线稳定生成正确课程”的验收目标。** 不能用上面两个通过样本替代全部失败样本。精进和面试还需要继续处理语义覆盖与事实质量，不建议把“关闭思考”直接等同于“质量与原来完全一致”。本次保持不放宽这些质量门槛。

本机自动化回归：**803 passed，1 个第三方弃用警告**。部署自检通过；已同步 152 个发布白名单文件，重启服务后首页与健康接口均 HTTP 200。未重置真实用户画像、学习进度或课件。

排查中还发现重连问题：中间层初版的 30 秒读取超时可能截断长流，导致 CLI 重试；现在由整次调用的绝对截止时间约束，不另外加 30 秒读取上限。驱动区别“临时重连后最终成功”和“终态失败”，避免把已成功恢复的请求误判失败。后台增加上游响应头、首批字节、错误类型和流错误数日志；**首批字节可能只是 SSE 元数据，不是正文首 token**。

## 如何自己看后台和复测

使用 `./run.sh`（macOS / Linux）或 `run.cmd`（Windows）启动后，在浏览器打开 `http://127.0.0.1:8787`。前后端同一端口。

保留启动终端，可看到类似：

```text
generation.start kind=plan research=False requested_reasoning=none
generation.finish kind=plan elapsed=... tool_calls=0 exit_code=0 usage={...}
```

`requested_reasoning=none` 只是请求设置；实际验收看 `reasoning_output_tokens`。`kind=lesson` 是课件调用；修正时会有第二次调用。必要研究路线会显示 `research=True`，允许检索工具。

独立真实模型测试：

```bash
python tools/evaluate_lessons.py --case beginner
python tools/evaluate_lessons.py --case advanced
python tools/evaluate_lessons.py --case interview
```

这些命令消耗自己的 DeepSeek 额度。报告保存在被 Git 忽略的 `evals/runs/`，包括每次模型输出、耗时和整条流程结果；勿把个人记录或密钥上传。

## 边界

- 真实样本从已确认画像起步，不是自然语言 onboarding 全覆盖测试。
- 模型输出通过结构与覆盖检查，不等于课程事实、难度和全部示例代码都经人工或编译验证。
- Windows 命令解析和 Python 3.10 回退有模拟回归，本次实机环境为 macOS；没有进行原生 Windows 端到端验收。
- 不承诺网络、供应商服务或任意未来输出永不失败。目标是减少不必要回合、避免已知误判、让失败不破坏原内容，并留下可复现证据。
- 后续改进建议：将课程的语义质量评审与格式校验明确分层；不要不断添加标题特例，或仅为通过正则而重复关键词。对于复杂并发等高风险教学内容，应对照官方契约与可执行测试审查，再考虑缓存复用。
