# Learning Agent 自适应分流、教学质量与练习反馈设计

**状态：** 已批准
**日期：** 2026-08-20
**范围：** 首次分流、水平诊断、教学启动、练习组合、答题反馈、内部质量评测
**不在本阶段：** GitHub 推送、公共知识库发布、多人 PR 工作流

## 1. 背景与基线证据

现有版本依赖 Codex 在自由对话中完成建档、确认、计划生成和开课。2026-08-20 使用四个隔离测试用户完成真实 DeepSeek/Codex 调用后，得到以下结果：

| 用户画像 | 当前开始教学轮数 | 教学内容评价 | 状态问题 |
|---|---:|---|---|
| Go 完全零基础、系统学习 | 3 | 生活化、课件丰富，但准备时间过长 | 第三轮才完成画像、计划和首课 |
| 零基础、知识库没有 webhook 重试主题 | 2 | 能从 Python 基础逐步连接目标 | 生成计划草案但 `active_plan` 为空 |
| 有一点 Python、围绕真实项目学习 | 2 | 请求流地图和第一小步清楚 | 画像与计划没有落盘；示例端口过时 |
| Go 熟练者专项精进 | 2 | 诊断题有区分度 | 一次给三道重题；`active_plan` 写成标题而非文件路径 |

共同问题：第一轮均未开始教学；已知信息会被重复询问；建档与计划写入由模型自由执行，结果不一致；高手诊断容易一次给太多内容。

## 2. 产品目标与成功标准

### 2.1 目标

1. 用户通过一次可点击的分流完成主要画像；不要求在聊天框描述自己的水平。
2. 零基础用户在第一次提交分流后立即进入第一课。
3. 学过一点或熟练用户通过 3–4 道点击式选择题完成诊断；根据答案可提前停止，任何情况下不超过 10 题。
4. 后端先确定性写入画像、计划路径和学习状态，再调用 Codex 开课。
5. 每次只讲一个核心概念，使用具体类比、最小示例、选择预测和动手证据逐步推进。
6. 每次 Skill、知识库或提示词变化后，可重新运行固定用户画像评测并比较质量。

### 2.2 可验收指标

- 零基础：1 次分流提交后展示第一课，不再追加摸底对话。
- 学过一点/熟练：1 次分流提交 + 1 组诊断后展示第一课。
- 诊断题：默认 3–4 题，硬上限 10；全部为按钮、单选卡或代码选项，不要求输入文字。
- 重复提问率：已选择字段不得再次出现在 Codex 问句中。
- 状态一致性：`profile_status=confirmed`；`active_plan` 必须是用户目录内真实 Markdown 文件的相对路径。
- 教学小步性：单轮最多一个新核心概念、一道当前选择题和一道可选动手题。
- 动效：答对后 1.2–1.8 秒结束；`prefers-reduced-motion` 下没有粒子位移。

## 3. 方案 A：一屏快速分流

### 3.1 首次分流卡片

用户第一次进入且没有确认画像时，中间学习画布显示分流卡片，右侧教练保持可见但输入区暂时不承担摸底任务。

必选字段：

1. **学习方式**
   - 从零系统学
   - 围绕一个项目学
   - 有基础，查漏补缺
   - 熟练者专项训练
2. **当前基础**
   - 完全没学过
   - 学过一点，能看懂简单例子
   - 能独立完成小功能
   - 有实际项目经验
3. **学习主题**
   - Python
   - Go
   - 项目路径
   - 自定义知识主题

提供默认值但允许展开调整：每次 25 分钟、每周 3–5 小时、先看例子再动手、分级提示。

主按钮文案：**“生成路线并开始第一小步”**。

### 3.2 分支规则

| 基础 | 下一步 |
|---|---|
| 完全没学过 | 跳过诊断，立即创建画像和计划并开课 |
| 学过一点 | 进入 3–4 道基础诊断选择题 |
| 能独立完成小功能 | 进入 3–4 道概念与调试选择题 |
| 有实际项目经验 | 进入 3–4 道迁移与工程判断选择题 |

项目学习用户的诊断围绕目标项目所需能力，不考与目标无关的语言冷知识。

## 4. 点击式自适应诊断

### 4.1 交互形式

- 每屏只出现一道题，2–5 个可点击选项。
- 代码题以只读代码块加选项呈现，例如“哪条执行路径会发生”“哪个修改最小且正确”。
- 用户点击后立即锁定该题、显示一句解释并进入下一题。
- 不在聊天框输入答案；诊断完成后才开放本节正常聊天。
- 顶部显示轻量进度，例如“诊断 2 / 4”，不显示考试分数。

### 4.2 题数与提前停止

- 初始题数目标为 3–4 题。
- 连续答案已经形成稳定判断时，3 题后提前停止。
- 答案互相矛盾或处于边界时，追加一题区分题。
- 任何分支最多 10 题；达到上限必须结束并以保守水平开课。
- 诊断只决定起点和练习密度，不给用户贴永久水平标签。

### 4.3 诊断维度

诊断引擎最多从以下维度选择与目标相关的 2–4 个：

- 运行与输出预测
- 数据与控制流
- 函数与模块边界
- 错误定位
- 并发或异步语义
- 测试意识
- 项目调用链阅读
- 迁移与工程取舍

题目必须携带 `concept_ids`、难度、正确选项、选项解释和下一题路由信息。前端不接收参考答案以外的模型自由文本作为评分依据。

## 5. 确定性画像与计划启动

### 5.1 后端职责

新增 onboarding 会话 API，由后端完成：

1. 校验分流选项和项目路径。
2. 按固定 Schema 写入 `$USER_DIR/profile.md`。
3. 生成并写入 `$USER_DIR/plans/<plan-id>.md`。
4. 将 `active_plan` 写成上述文件的相对路径。
5. 原子更新 `learning-state.json`，追加 onboarding 事件。
6. 返回结构化第一课上下文。

Codex 不再负责“是否可以写画像”的自由判断。它收到的系统上下文必须包含：画像已确认、诊断摘要、当前课、不得继续摸底、立即开始一个核心概念。

### 5.2 知识库存在与缺失

- 有对应知识原子：计划引用知识库概念、Deck 和题目。
- 没有完整主题：先引用已有先修概念，再建立 `knowledge_gap`，教学中把经过验证的讲解、误区和练习送入策展队列。
- 知识缺失不能阻塞第一课；用户先学目标所需的最小先修。

## 6. 教学循环与质量规则

每一小节采用固定但可适配的循环：

1. **为什么**：用目标相关的具体问题说明价值，不以术语定义开场。
2. **生活化类比**：只服务当前概念，避免一次引入多个新名词。
3. **最小示例**：代码短到能在一屏内理解。
4. **点击预测题**：先让用户判断输出、路径或原因。
5. **动手题**：修改、追踪、调试或生成一个新例子，形成真实证据。
6. **评价**：结论 + 一个具体优点 + 一个关键问题 + 一个下一步动作。
7. **沉淀**：写入练习记录和复习讲义，再解锁下一个概念。

硬规则：

- 每轮最多一个新核心概念。
- 默认只展示一道当前题，不一次抛出三道大题。
- 错误时先给最小提示，不直接给答案。
- “跳过”不算正确，不写入掌握证据，也不触发庆祝。
- HTML Deck 必须按页保存进度；用户回到页面时恢复当前页和检测门状态。

## 7. 练习组合

### 7.1 选择题

用于快速预测、概念辨析、执行路径和错误定位。用户点击即可作答，立即收到短解释。选择题可以形成 `introduced` 或诊断证据，但不能单独证明独立掌握。

### 7.2 动手题

用于修改代码、运行验证、解释实际输出、追踪调用链或完成小功能。动手题必须说明：在哪里做、怎么运行、提交什么、完成标准是什么。只有真实产物和运行证据才能推进较高掌握度。

### 7.3 自适应组合

- 零基础：1 道选择预测 + 1 道极小改写。
- 学过一点：1 道选择诊断 + 1 道追踪或修复。
- 熟练者：选择题只做快速定位，主要证据来自迁移、调试和工程取舍题。

## 8. 答对庆祝与错误反馈

采用“进度绽放”动效：

- 正确答案或动手证据通过后，成功卡边框转为 sage，terracotta 进度线推进，4–8 个纸片元素短暂上浮。
- 动效 1.2–1.8 秒，不阻塞继续按钮，不播放声音。
- 只庆祝有评分依据的真实正确；跳过、查看答案或模型无法验证时不庆祝。
- 错误反馈不震动、不闪红；保持原页面，显示一个最小线索和“再试一次”。
- 支持 `prefers-reduced-motion`，设置中提供关闭庆祝动画开关。

本网页直接使用原生 Web Animations API/CSS motion。当前可用的 Adobe Animate 工具仅适用于 Adobe Express 文档，不适合网页运行时，因此不作为依赖。

## 9. 数据契约

### 9.1 Onboarding 提交

```json
{
  "user_id": "yang",
  "learning_mode": "systematic|project|gap_filling|advanced_practice",
  "level_claim": "zero|some|independent|experienced",
  "topic": {"type": "python|go|project|custom", "value": "..."},
  "session_minutes": 25,
  "weekly_minutes": 240,
  "teaching_preference": "example_then_practice"
}
```

### 9.2 诊断题

```json
{
  "question_id": "go.concurrent.loop-capture.v1",
  "prompt": "这段程序可能输出什么？",
  "code": "...",
  "options": [
    {"id": "a", "label": "..."},
    {"id": "b", "label": "..."}
  ],
  "concept_ids": ["go.concurrency.loop-variable"],
  "difficulty": 3
}
```

评分结果由后端返回 `correct`、短解释、当前诊断置信度、是否结束和下一题；正确选项不由前端自行推导。

## 10. 内部评测体系

### 10.1 固定画像

1. 零基础，知识库有：Go 系统学习。
2. 零基础，知识库缺失：Python webhook 重试 API。
3. 有基础，围绕真实 Python 项目学习。
4. 熟练者：Go 并发与错误处理精进。

### 10.2 自动指标

- `turns_to_first_teaching`
- `duplicate_question_count`
- `diagnostic_question_count`
- `first_response_latency_ms`
- `profile_persisted`
- `active_plan_resolves`
- `one_core_concept_per_turn`
- `has_concrete_example`
- `has_click_question`
- `has_hands_on_task`
- `completion_criteria_present`
- `unsupported_mastery_claim_count`

### 10.3 人工质量量表

每个场景按 1–5 分评价：生动形象、深入浅出、小步推进、目标相关、练习质量、反馈质量、状态一致性。任一场景出现重复摸底、超过两步才开课、计划无法读取或跳过被记为正确时，整轮评测不能通过。

原始模型输出、事件时间和评分结果保存到隔离的 eval 目录；不得写入真实用户画像，也不得自动进入公共知识库。

## 11. 错误处理

- 项目路径无效：在分流卡内提示并允许重新选择，不进入 Codex 对话。
- 诊断题生成失败：使用知识库内固定题；仍失败则按自述水平保守开课。
- 画像或计划原子写入失败：回滚本次 onboarding 状态并显示可重试错误。
- Codex 首课超时：计划和画像保持有效，前端展示确定性的第一小步骨架和重试按钮。
- 评分不可验证：标记“需要人工/运行证据”，不触发庆祝和掌握度更新。

## 12. 测试与验收

- 单元测试：分流规则、诊断提前停止、10 题上限、状态路径校验、跳过不计正确、动效偏好。
- API 测试：onboarding、diagnostic next/answer、first lesson context、原子写入回滚。
- 浏览器测试：全程只点击完成诊断；零基础无需诊断；键盘可操作；移动端不遮挡；减少动态效果生效。
- 真实调用回归：四画像各至少一轮，对照基线记录开课轮数、延迟、内容与状态。
- 视觉 QA：在现有暖象牙、charcoal、terracotta、sage 设计体系内实现，不引入新的视觉语言。

## 13. 分阶段交付

1. **Phase B1：确定性 onboarding 与选择式诊断**——解决开始慢和状态不一致。
2. **Phase B2：小步教学契约与选择题/动手题编排**——解决一次给太多内容。
3. **Phase B3：庆祝动效与错题反馈**——改善练习反馈体验。
4. **Phase B4：真实四画像评测与质量报告**——验证改动效果并形成长期回归门禁。
