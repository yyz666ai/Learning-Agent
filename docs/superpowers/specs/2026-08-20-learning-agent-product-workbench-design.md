# Learning Agent 学习工作台 PRD

> 版本：v3.0 设计稿
> 日期：2026-08-20
> 产品形态：本地优先的 AI 学习工作台
> 技术底座：前端 Web App + FastAPI + Codex CLI harness + DeepSeek API

## 1. 产品定位

Learning Agent 不是“可以聊学习的 AI”，而是一个能持续读取用户目标、基础、时间和学习证据，然后动态组织课程、教学、练习、评价与复习的个人学习系统。

一句话体验目标：

> 用户每次打开产品，都知道自己在学什么、为什么学、下一小步做什么，做完后又能得到可解释的反馈。

## 2. 产品目标

### 2.1 用户目标

1. 零基础学习者不需要自己设计课程，能从最小的第一步开始。
2. 有基础的学习者不必重复已会内容，可以通过证据跳过或压缩阶段。
3. 以项目为目标的用户能从目标代码反向得到必要知识路线。
4. 用户不仅“看懂”，还能通过习题、迁移任务和延迟复习形成掌握证据。
5. 所有学习过程最终形成一份可阅读、可检索、可持续更新的个人讲义。

### 2.2 平台目标

1. 将知识、教学方法、用户状态和呈现方式分离。
2. 让知识库可通过 GitHub PR 方式公开协作和持续增长。
3. 保留 Codex CLI 作为 harness，前端不感知模型与工具调用细节。
4. 使每个关键学习动作都有结构化事件，不再从自然语言中猜测课件或作业。

## 3. 非目标

- 首版不做课程商城、付费、直播或班级管理。
- 首版不做通用 LMS，不把产品变成课程文件仓库。
- 首版不用一个百分比宣称“掌握程度”。
- 首版不依赖课件内部的答题结果直接判定 mastered。
- 首版不在未经验证时一次性生成整个新领域的所有知识原子。

## 4. 核心用户类型

### 4.1 小白·知识库已有

例如零基础学 Go。系统使用已有 concept map、learning path、atoms 和 deck，按学习证据选择起点。

### 4.2 小白·知识库没有

例如学习一个新库或新技术。系统先建立带来源与版本的路线骨架，教到哪里才沉淀哪个 atom/deck/exercise。

### 4.3 小白·基于项目学

例如“为了看懂这个 Go 服务而学 Go”。系统先定义最终能力，再绘制代码地图、知识地图和差距地图。

### 4.4 熟练者·精进

用户以习题、迁移题、综合题和小项目改造为主，教学内容只在暴露知识缺口时出现。

## 5. 产品原则

1. **学习计划驱动，聊天辅助**：聊天是教练，不是信息架构。
2. **一次一个可验证目标**：屏幕上始终有唯一的主任务。
3. **读完不等于学会**：理解、辅助完成、独立完成和延迟复习分开。
4. **学习者看人话**：不展示 revision、atom ID 或内部事件等调试字段。
5. **内容可追溯**：新知识有来源、版本、编辑和验证记录。
6. **课件是状态机**：页面、检测门、进度和完成事件必须可被外层应用识别。

## 6. 信息架构

### 6.1 桌面端三区工作台

#### 左侧：学习路线

- 当前学习目标。
- 分阶段教学大纲。
- 当前节点、已完成证据、待复习节点。
- 可切换“路线 / 讲义 / 错题”，但不用会话列表占据主导位置。

#### 中间：学习画布

- 默认呈现当前课节，而非聊天消息。
- 可切换教材、HTML deck、习题、项目任务和复习文档。
- 底部只保留一个核心动作：继续学习、提交答案或进入下一步。

#### 右侧：AI 教练

- 流式对话、当前知识点解释、L0–L5 提示、答题评价。
- 默认宽度较窄，可收起，避免聊天压过学习内容。
- 在移动端转为底部抽屉。

### 6.2 顶部状态

- 目标名称、本次预计时长、学习状态。
- 保存状态、Codex 工作状态和流式连接状态使用明确文字，不仅依赖颜色。

## 7. 端到端学习流程

### 7.1 第一次使用或目标变更

1. 用户输入想学的东西或项目路径。
2. 系统检测现有画像与新目标是否冲突。
3. 使用一组逐步建档卡片收集最少必要信息：目标、基础证据、每周时间、单次时长。
4. 展示“我理解的你”摘要，用户确认后才写入状态。
5. Codex 生成 `$USER_DIR/plans/<plan-id>.md`，同时生成前端可直接渲染的 plan JSON 索引。
6. 页面进入计划概览，强调当前第一步，不要求用户一次阅读全部计划。

### 7.2 日常学习

1. 打开应用后恢复当前课节、deck 页和未提交作答。
2. 展示“今天只做这件事”和预计用时。
3. 先读一小段教材或 deck，然后完成一个预测或小练习。
4. 提交后给出结论、一个优点、一个关键问题和下一步。
5. 未达到完成标准时进入最低必要提示，不直接给完整答案。
6. 完成后记录学习事件，更新计划节点，并告知下一步。

### 7.3 复习

1. 系统从已到期项中选择最多 5 个，但每次只呈现 1 题。
2. 不显示旧答案，先要求无提示回忆、解释或迁移。
3. 完成评价后才更新下次间隔和掌握证据。

### 7.4 教材式复习讲义

`$USER_DIR/notes/<plan-id>.md` 按计划节点组织，不是聊天摘要。每个节点包含：

- 用户能理解的概念解释。
- 已完成的代表性练习与用户自己的答案。
- 重复误区、最高提示等级和纠正方法。
- 最终独立迁移任务。
- 下次复习日期与建议。

## 8. HTML Deck 交互契约

### 8.1 知识资产

每个可教 atom 至少包含：

- `<atom-id>.md`：事实源和教学规格。
- `<atom-id>.deck.html`：可交互呈现。
- `<atom-id>.exercises.json`：结构化习题与评分标准。

### 8.2 Deck 事件

Deck 与宿主页通过 `postMessage` 交换结构化事件：

- `deck.ready`：返回 atom ID、版本、页数和当前页。
- `deck.page_changed`：当前页和页面类型。
- `deck.checkpoint_started`：检测门开始。
- `deck.answer_submitted`：结构化作答，不直接声称掌握。
- `deck.completed`：课件完成，包含完成页和检测门摘要。
- `host.restore`：恢复上次页面和未完成作答。

### 8.3 课件可用性

- 支持键盘上一页/下一页、明确焦点和屏幕阅读文本。
- 不使用颜色作为唯一答题结果。
- 不可将焦点锁在 iframe 内。
- 小屏下自适应，不依赖固定 1280×720 的等比缩放才可阅读。

## 9. 习题与评价

### 9.1 题型

- 预测题：预测输出或执行顺序。
- 概念题：用自己的话解释。
- 短代码题：在内嵌编辑器或用户 workspace 作答。
- 调试题：根据错误现象定位原因。
- 迁移题：结构相同、表面不同的新场景。
- 项目里程碑：以可运行产物与解释作为验收。

### 9.2 题目结构

题目至少包含 `exercise_id`、`atom_id`、`kind`、`prompt`、`instructions`、`completion_criteria`、`rubric`、`difficulty`、`version`、`source`。

### 9.3 学习者指引

每道题都必须明确说明：

- 这道题练什么。
- 在哪里作答。
- 需要提交什么。
- 怎样算完成。
- 卡住时如何获取提示。

### 9.4 评价输出

1. 结论：正确、部分正确、需要重做。
2. 一个具体优点。
3. 最关键的一个问题。
4. 证据归类：independent、assisted 或 insufficient。
5. 下一个独立动作。

## 10. 学习路由

### 10.1 路由输入

- 已确认目标。
- 自述基础与诊断证据。
- 已有独立/辅助证据。
- 可用时间。
- 知识库覆盖状态。
- 是否有目标代码库。

### 10.2 路由决策

1. 目标变更或画像未确认：`learner-onboarding`。
2. 有目标仓库但无差距地图：`codebase-learning-plan`。
3. 知识库无对应领域：`knowledge-curator` 先建路线骨架。
4. 有独立证据：压缩或跳过节点。
5. 有辅助证据但无独立证据：保留迁移题。
6. 零基础：从环境与最小执行闭环开始。
7. 熟练者：从诊断、迁移题或项目任务开始。

## 11. FastAPI 与流式输出

### 11.1 API 形态

- `POST /api/chat/stream`：SSE 流式对话。
- `GET /api/learning-context`：画像摘要、当前计划、当前任务和复习摘要。
- `GET /api/plans/{plan_id}`：计划文档与可渲染结构。
- `GET /api/lessons/{atom_id}`：atom、deck 和习题资产。
- `POST /api/exercises/{exercise_id}/attempts`：提交作答并获得结构化评价。
- `GET /api/notes/{plan_id}`：教材式复习讲义。

### 11.2 SSE 事件

- `session.started`：会话和请求 ID。
- `status`：正在读取计划、选择 Skill、生成课节或评价等用户可理解状态。
- `message.delta`：逐段文本。
- `artifact`：结构化 plan、lesson、deck、exercise、review-note 信息。
- `state.changed`：修订号和可见变化摘要。
- `message.completed`：最终回复与用量摘要。
- `error`：可恢复错误、重试建议和 request ID。

### 11.3 流式前端规则

- 先创建空消息容器，按 delta 追加内容。
- 服务器事件与渲染分离，不每个 token 重新解析全部 Markdown。
- 页面离开、用户取消或新请求时通过 `AbortController` 终止连接。
- 中断后保留已生成内容，提供“继续生成”而非丢失全部内容。

## 12. 用户数据结构

```text
$USER_DIR/
├── profile.md
├── learning-state.json
├── plans/
│   ├── <plan-id>.md
│   └── <plan-id>.json
├── sessions/
│   └── <session-id>.jsonl
├── attempts/
│   └── <exercise-id>.jsonl
├── mastery/
├── reviews/
├── notes/
│   └── <plan-id>.md
├── history/
└── workspace/demos/
```

前端 localStorage 只保存可抛弃 UI 偏好和未提交草稿，不再是学习记录的事实源。

## 13. 知识库结构与公共协作

### 13.1 建议结构

```text
curriculum/<domain>/
├── manifest.yaml
├── concept-map.json
├── learning-paths/
├── atoms/
│   ├── <atom-id>.md
│   ├── <atom-id>.deck.html
│   └── <atom-id>.exercises.json
├── sources/
└── evals/
```

### 13.2 PR 合并门禁

1. 文件命名、frontmatter 与 Schema 通过。
2. atom 所属 concept 和所有 prerequisite 存在。
3. atom 与 deck/exercises 配对完整。
4. deck 能无网络运行，通过溢出、键盘、事件契约和基础可访问性检查。
5. 习题有完成标准和评分 rubric，且不泄露答案。
6. 版本敏感内容包含权威来源、访问日期和适用版本。
7. 至少有一个行为评估或人工教学验收记录。

## 14. 视觉与交互方向

- 整体气质：安静、专注、有编辑感和知识感，不做儿童化卡通。
- 基础色：纸张暖白或低饱和中性色，使用一个克制的学习强调色。
- 排版：长文阅读舒适，代码和教材拥有清晰层级，不追求过密的仪表盘。
- 进度：用路线节点、完成证据和下一步表达，不用伪精确百分比。
- 动效：只服务于流式输出、页面过渡、作答反馈和焦点移动。

## 15. 响应式与可访问性

- ≥1200px：三区工作台。
- 768–1199px：左侧路线收成可展开栏，AI 教练保持右抽屉。
- <768px：学习画布为主，路线与教练分别为左/底抽屉。
- 所有核心动作可键盘完成，具备可见焦点。
- 状态变化提供文字与无障碍播报。
- 流式文本不强制屏幕阅读器逐 token 播报，而是按语义块更新。

## 16. 成功指标

### 产品体验

- 新用户完成建档后，能在一个页面内说明目标、当前任务和下一步。
- 流式连接在开始请求后尽快返回可理解状态，不再长时间只显示等待动画。
- 用户离开再返回时，可恢复课节位置和未完成作答。

### 学习效果

- 每个已完成课节都有对应学习证据，而非只有阅读时长。
- 使用 L4 参考答案后必须出现 L5 迁移任务。
- 复习讲义能回溯代表作答、反馈、误区和迁移证据。

### 知识库健康

- CI 能阻止缺少 deck/exercises 或先修关系错误的 atom。
- 行为评估不得以 0 条用例静默成功。
- 每个新领域都能追溯来源、版本和贡献者。

## 17. 分阶段范围

### 阶段 A：产品骨架

- FastAPI + SSE 流式对话。
- 学习工作台三区布局。
- 计划文档 API 和常驻渲染。
- 学习记录从 localStorage 迁移到用户目录。

### 阶段 B：学习闭环

- 结构化习题、作答、批改和提示轨迹。
- Deck postMessage 契约与恢复。
- 错题与教材式复习讲义。

### 阶段 C：知识共建

- 知识资产 Schema、完整性 validator 和 CI。
- GitHub PR 模板、贡献指南和教学验收流程。
- 领域 manifest 与版本发布。

## 18. 风险与对策

| 风险 | 对策 |
|---|---|
| Codex 一次性 exec 导致首段输出慢 | 先流式转发已有 JSONL 事件，再评估常驻 app-server |
| 旧计划路径和新契约冲突 | 应用层兼容读取旧 `learning-plan.md`，只将新计划写到 `plans/` |
| Deck 中任意 JS 带来安全风险 | 保持 iframe sandbox，限制事件 Schema 和来源，不授权同源 DOM |
| AI 评分不稳定 | 前端确定性检查 + rubric + Codex 证据审核分层，保留原始作答 |
| 自生长知识库变得混乱 | 使用领域 manifest、稳定 ID、版本、来源和 PR 门禁 |
| 功能过多导致界面信息过载 | 以当前学习任务为唯一主角，次要功能收入导航和抽屉 |

## 19. 验收场景

1. 新用户输入“零基础学 Go”，完成最少建档后生成计划，并立即看到第一任务。
2. 用户切换学习目标时，系统保留旧计划，但不把旧证据误用到新领域。
3. 打开 Go 第一课，刷新页面后仍回到原 deck 页。
4. 完成课件检测门不会直接标记 mastered；完成独立迁移后才产生 independent 证据。
5. 习题明确显示如何作答、提交什么和完成标准；提交后得到结构化反馈。
6. 聊天可见流式输出，中途取消不丢失已有内容，错误时可继续生成。
7. 打开复习讲义，能看到已学概念、代表作答、错误反馈和下次复习日期。
8. 添加一个新 FastAPI atom 的 PR 缺少 deck 或 exercises 时，CI 必须失败并说明原因。

## 20. 待视觉方向选定后确认

- 最终字体、色板、间距、图标系统和动效节奏。
- 左侧路线的节点密度和折叠方式。
- AI 教练默认展开宽度与中屏行为。
- Deck 在中间画布的页面比例和辅助导航。
