# 面试题库持续学习系统设计

**状态：** 用户授权直接实施

**日期：** 2026-08-20

**依赖：** `2026-08-20-chat-first-adaptive-learning-design.md`

**目标：** 用户通过聊天或语音转写持续提交来源不一、可能没有答案的面试题；Learning Agent 保留原始材料、形成结构化岗位题库，提供逐题或系统学习，扩展关联题，并在题库增长时保护已经取得的学习进度。

## 1. 方案比较与选择

### 方案 A：按采集批次保存

每次粘贴的题目独立成一组，按时间顺序学习。实现简单、来源清楚，但同类题会重复，无法形成前端岗、后端岗等完整知识体系。

### 方案 B：直接写入一棵岗位知识树

所有问题立即归入岗位、领域和知识点。检索和系统学习最好，但容易丢失原始语境，也难以解释某道题来自哪次语音转写。

### 方案 C：原始批次 + 岗位知识树（采用）

原始语音转写按批次不可变保存，标准化问题通过稳定 ID 去重并归入岗位知识树。采集来源与系统学习兼得；新增题目只追加知识节点，不覆盖旧题、旧答案或旧掌握证据。

## 2. 用户流程

### 2.1 收集入库

1. 用户在面试路线的聊天框中粘贴或语音输入一个或多个问题。
2. 系统识别候选题目，在输入框上方显示“检测到 N 道题”的轻量确认条。
3. 后端保存完整原始文本，再做分题、标准化、去重和初步分类。
4. 返回新增、重复、待确认和无法识别的数量；不因重复题建立第二份掌握记录。
5. 没有答案的题目允许入库，`answer_status=missing`，不能伪装成已解答。

原始文本和标准题目同时保留：原文用于追溯，标准题目用于搜索、讲解、判分和知识关系。

### 2.2 选择讲解方式

每次完成入库后，聊天输入框上方只显示三个选项：

- **逐题从头讲：** 按采集顺序，每题建立直觉、答案结构、追问和复述。
- **按知识体系讲：** 先按先修关系重排，再生成系统课程和 HTML PPT。
- **先做水平测试：** 用 3–4 道题定位已掌握部分，再决定哪些快进。

选择题仍是可点击的 inline choice tray，不要求用户重新打字。

### 2.3 系统学习与拓展

系统针对目标岗位建立知识树，例如后端岗可分为语言基础、并发、网络、数据库、缓存、消息队列、系统设计、工程与行为面试。

每道采集题可以产生三类关联题：

- 前置题：回答当前题之前必须理解什么。
- 变式题：换条件、换代码或换场景，检验迁移能力。
- 追问题：模拟面试官继续深挖边界、取舍和故障。

模型生成的扩展题先标记 `origin=expanded`、`review_status=draft`，与用户采集题区分。只有通过重复检测、答案/rubric 校验和策展流程后，才能进入共享知识库；在此之前只属于当前用户题库。

### 2.4 动态更新计划但不回退进度

新增问题触发 `PlanReconciler`：

1. 计算新题与现有知识节点的覆盖关系。
2. 已在计划内的题只增加来源，不改计划。
3. 新题若属于当前阶段，加入该阶段的待学习池。
4. 新题若属于后续领域，追加到后续阶段或题库 backlog。
5. 已完成阶段、掌握证据、复习记录和作业记录永不重置。

左栏同时显示两个指标，避免“题库变大导致看起来退步”的错觉：

- **主计划进度：** 单调不下降；以已承诺学习范围和完成证据计算。
- **题库覆盖率：** 已掌握题数 / 当前题库总数；新增题时分母可以变化。

计划记录 `progress_floor`。重新规划后的显示进度不得低于旧值，但毕业仍要求完成当前题库的必修知识节点，不能用进度保护掩盖新增缺口。

## 3. 左侧栏设计

当前学习项目下增加“大纲 / 题库”切换，不增加新的全屏导航体系。

题库视图显示：

- 岗位题库名称和题库覆盖率。
- 按领域折叠的题目分组。
- 每道题的回答状态：缺少回答、草稿答案、已验证答案。
- 每道题的掌握状态：未学习、学习中、较困难、已掌握。
- 来源标记：用户采集、系统扩展、共享知识库。

点击题目后，中央 ArtifactPane 打开题目讲义、代码、标准答案结构和关联问题；右侧对话用于回答、追问、评价和下一步。左侧不承担答题操作。

## 4. 数据结构

```text
userdir/u_<user>/interview-bank/
├── bank.json
├── sources/
│   └── <batch-id>.json
├── questions/
│   └── <question-id>.json
├── relations.json
└── intake-events.jsonl
```

### 4.1 原始批次

- `batch_id`
- `raw_text`
- `input_method`: text / voice_transcript
- `created_at`
- `question_ids`
- `parse_warnings`

### 4.2 标准题目

- `question_id`：基于标准化文本生成的稳定 ID。
- `raw_variants`：原始说法与来源批次。
- `normalized_text`
- `role`、`domains`、`concept_ids`、`difficulty`
- `origin`: collected / expanded / shared
- `answer_status`: missing / draft / verified
- `answer_markdown`、`rubric`、`related_question_ids`
- `mastery_status`: unseen / learning / hard / mastered
- `evidence_refs`、`next_review`
- `plan_node_id`

`answer_status=verified` 必须有知识库来源、客观测试或人工/模型 rubric 校验记录；只有语言流畅不能算验证。

## 5. 服务边界

- `InterviewIntakeService`：保留原文、分题、标准化、稳定 ID 和去重。
- `InterviewTaxonomyService`：岗位、领域、知识点和先修关系。
- `InterviewAnswerService`：答案状态、rubric 和关联题扩展。
- `PlanReconciler`：把新题增量合并进计划，保护进度与证据。
- `InterviewBankRail`：左栏题库分组、回答状态和掌握状态。

共享知识库依旧由 `knowledge-curator` 管理。普通用户提交的题目先进入个人题库，不能自动污染公共母本。

## 6. API

- `POST /api/interview/intake`：提交原始文本并返回解析、去重和分组结果。
- `GET /api/interview/bank`：返回左栏所需的题库摘要与分组。
- `GET /api/interview/questions/{id}`：返回单题详情，不暴露私有判分答案。
- `POST /api/interview/questions/{id}/study-mode`：选择逐题、系统或先测评。
- `POST /api/interview/questions/{id}/mastery`：基于评价证据更新掌握状态。
- `POST /api/interview/reconcile-plan`：增量更新计划并返回变更摘要。

所有写入限制在当前用户目录，使用安全用户 ID、原子写入和稳定 revision。

## 7. 错误处理

- 语音转写无法可靠分题：保存原文，标记 `parse_warnings`，不丢数据。
- 重复问题：合并来源和原始说法，不重置答案或掌握度。
- 模型分类失败：进入“待分类”，仍可逐题学习。
- 没有答案：明确展示“缺少回答”，允许从讲解流程生成草稿。
- 扩展题质量不足：保留在个人草稿区，不进入共享知识库。
- 计划合并失败：保留旧 plan 和旧进度，返回可恢复错误。

## 8. 测试与验收

### 8.1 确定性测试

- 多题文本分割、中文问号与编号解析。
- 原始文本完整保留。
- 同题不同说法去重和稳定 ID。
- 缺少答案可以入库且状态准确。
- 新题合并不降低 `progress_floor`，不删除完成节点。
- 左栏正确显示回答状态和掌握状态。
- 用户题与扩展题来源清晰。

### 8.2 真实模型回归

- 一次粘贴 10 道无答案后端面试题。
- 重复追加 3 道旧题和 5 道新题。
- 选择逐题讲解、系统讲解和先测评三种模式。
- 验证扩展问题覆盖前置、变式和追问，而不是同义改写。
- 验证面试回答使用简答、追问和 rubric，不退化成大量选择题。

### 8.3 浏览器验收

- 题目通过聊天输入后，左栏无需刷新即可出现。
- 左栏能同时看到回答状态和掌握状态。
- 点击题目在中央打开，右侧对话保持上下文。
- 新增问题后主计划进度不下降，题库覆盖率独立更新。
- 桌面和移动端无横向溢出。
